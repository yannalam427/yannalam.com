How the alert gets to a phone

A CBW network relay controller publishes an MQTT message when a predefined condition occurs. HiveMQ distributes the message, a Node-RED flow running on a Raspberry Pi processes it, and Pushover delivers the notification to a phone.

Why this path

The goal was to supplement the booth indicator, not replace it. An email-based alert took about seven seconds to arrive, so I explored MQTT, which got the alert to a phone in about two seconds. Each piece has one job: the broker distributes messages, Node-RED makes the workflow easy to configure, and Pushover handles delivery to phones.

2HNTB · Field troubleshooting

Troubleshooting a three-zone over-height detection system

During a site visit to the Lincoln Tunnel, I supported troubleshooting of an over-height detection system with three advance detection zones. Alerts reached the control booth correctly, but some fault conditions did not. By the time we left the site, it was fixed.

My role
Supported field troubleshooting
Result
Resolved before we left the site

The problem

When alert conditions were forced, they showed up correctly at the control-booth panel and on SCADA. When fault conditions were forced, they could reach the communications cabinet without lighting the matching fault indicator in the booth.

How we narrowed it down

We reviewed the wiring diagrams, the cabinet terminations and the normally open versus normally closed contact logic. Because the alert path worked for all three zones, the problem could be narrowed to the fault-indication path.

What we found

One thing we found was that the zones appeared to use inconsistent contact configurations.

The result

By the time we left the site, the faults were showing up in the booth as they should, and separate SCADA faults we saw that day had been cleared as well.

4HNTB · Proof of concept

Standards retrieval

I helped develop an AI-assisted retrieval proof of concept using structured indexes of engineering references with Microsoft Copilot and SharePoint. A plain-English question returns the standard drawings and specification sections that are likely relevant, along with related references.

Indexed
323 standard drawings, 126 spec sections
Built with
Microsoft Copilot, SharePoint

Try itPick a question to see what the index finds

Sample documents written for this site. These are not HNTB or agency standards. In the real tool, engineers still check the official source.

How it works

Each reference gets a structured index entry. The AI interprets a natural-language question and matches it to drawings and specification sections that may apply. It can also surface related references: a CCTV installation, for example, brings up the conduit, cabinet and grounding material that goes with it.

What gets indexed

Standard drawings: title, standard ID, document type, discipline, category, project needs, keywords, related standards, revision date, source link, status and notes. An enriched version added search aliases, common use cases, installation context and confidence tags.

Specification sections: section number and title, division, discipline, scope summary, keywords, common applications, related sections, source information, verification status and use limitations.

In total that’s about 450 indexed references: 323 standard drawings and 126 specification sections.

What it doesn’t do

It supports document discovery and early research. Engineers still review the official sources, and the tool doesn’t decide compliance or evaluate every clause of a specification.

5Personal project · Feb–Mar 2026

Aircraft approach display

A Python backend pulls live aircraft positions from the OpenSky Network and filters them for planes descending toward Newark Liberty (EWR) inside my viewing window. It adds aircraft and route details from adsbdb and FlightView, and formats four 20-character lines that an ESP32 shows on an LCD, in step with the planes I can see landing.

Built with
Python, ESP32, OpenSky Network, adsbdb

Try itTap a plane to see how the filters treat it

  1. OpenSky + adsbdb
  2. Python backend
  3. ESP32
  4. LCD
ESP32 · 20×4 LCDSimulated

Simulated traffic with made-up flight numbers. The filters are the ones the backend uses. They describe my viewing window, not whether a plane is cleared to land.

How it picks a plane

The backend searches a box around Newark and the nearby airspace, then keeps aircraft that are:

  • between 600 and 1,700 ft (barometric altitude)
  • on a ground track between 190° and 220°
  • descending at 250 ft per minute or more
  • 1.5 to 5.5 nautical miles from EWR

Aircraft missing the position or flight data those filters need are rejected. If more than one plane matches, it favors the one closest to 1,150 ft and 3.2 NM out. That’s where planes are easiest to see from where I watch.

Where the data comes from

Live aircraft states come from the OpenSky Network. Aircraft and route details come from adsbdb, with Newark’s FlightView arrivals feed as supplemental route information. The backend formats everything into four lines of up to 20 characters, and the ESP32 displays what the backend sends.

Handling messy data

Route data doesn’t always line up with the live position data. The backend checks the callsigns that come back, tries alternate callsign formats, and confirms that the destination is actually EWR before showing a route.

Smart parking garage occupancy system

A team proof of concept for NJIT’s Fundamentals of Engineering Design course, aimed at how hard it is for commuters to find parking. The system detected open spaces, used a screen to point drivers to the nearest one, and updated a website with live availability as conditions changed.

How it works

An Arduino Uno reads a sensor at each space and marks it available or occupied. The screen shows how many spaces are open and points drivers to the nearest one, and status lights mark each space. A Wi-Fi module sends the same readings to the website, so when a space changes, the site shows it in near real time.
